# Intent: Adopt the AI-native SDLC Playbook in the templates and the root

Author: Joe Takara (Developer Productivity). Status: accepted.

## Problem

The templates and the root have never followed an SDLC; they adopt the AI-native SDLC Playbook for the first time. A play-by-play check of `main` against the playbook found plays that are not set up yet and plays that are only partly set up. ## Proposed outcome

Every play the playbook describes is present in the templates, and in the root where it applies, or its absence is recorded with the playbook page and the reason. By play, in the playbook's stage order:

- **Intent home (12–13):** every change keeps its intent, spec, and plan in its own folder in `intent/`, where the playbook commits them as the audit trail (pages 7 and 20); none is deleted or moved, as in the community repositories that implement this playbook (`imsungbin/ai-native-sdlc-playbook`, `matthew-js-porter/spring-petclinic-ai-native`, `jsnkle/ai-native-sdlc`), which keep one folder per change in `intent/`.
  - A folder keeps the short kebab-case name `intent/<change>/` that the `write-intent` skill and `AGENTS.md` already use, as `jsnkle/ai-native-sdlc` keeps one folder per change named with a short slug; when each change was made is in git history (page 13).
  - Each intent's `Status:` line, which the playbook's example starts at `draft` (page 13), shows where the change stands. The playbook shows no other value; `accepted`, `done`, `withdrawn`, and `replaced by intent/<change>/` are this intent's proposal, which the spec confirms. The agent or the CI job that carries out each step writes the line in the pull request it opens, not a person by hand. Until the line catches up, the status skill reads acceptance from the merge of the intent's pull request itself, so a stalled handover still shows the intent as accepted.
  - A rejected intent stays as a file with `Status: rejected.`, because its pull request merges (`templates/base/intent/README.md`). A problem found after a change ships starts a new intent, as the playbook's closing loop does (page 48), instead of editing the old one.
  - The write-intent skill and `intent/README.md` describe this, in the root and in every template.
- **Automated handover (5, 9, 16):** when an intent's pull request merges, a non-interactive CI job runs the spec pass with the organization's skills loaded and opens `spec.md` as a pull request, as page 16, step 2 describes, so "the product owner's first involvement is the review". The job runs with the same exact allowlist (step 3 below) and the same Claude credentials as the project's other Claude jobs: an API key in the templates, workload identity federation in the root. A community implementation of the playbook ships such a job as `spec-on-intent-merge.yml` (`jsnkle/ai-native-sdlc`, `plugin/template/.github/workflows/`). A pull request that a workflow opens with the repository's `GITHUB_TOKEN` starts its checks only after a person with write access selects **Approve workflows to run**, and a push made with that token starts no workflow ([GitHub Docs: GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token), from `github/docs` `data/reusables/actions/actions-do-not-trigger-workflows.md`); the community kit `jsnkle/ai-native-sdlc` uses a separate token, `LOOP_GH_TOKEN`, for this reason. The spec decides which token the job uses, and `SETUP.md` says who creates it. The decisions stay with people, where the playbook puts them: the product owner accepts the intent and the spec (page 16, step 6), and the engineer approves the plan in plan mode (page 19). In the root and in every template.
- **Interviews in Plan and Build (12, 19–20):** the agent knows how to interview from the project's own files, so no one has to remember to ask for it:
  - The `write-intent` skill and the plan convention in `AGENTS.md` both tell the agent to interview the person in rounds: number each question, offer choices where it can, give its recommended answer, look up every fact itself and ask only for decisions, use the person's own words and plain language (page 12, step 1: "No formal language is required"), and stop only when nothing is left silently assumed. This follows Claude Code's own guidance, "Interview me until you could write the spec", where Claude "comes back with multiple-choice questions about the parts you haven't pinned down" and "keeps asking until the answers add up to a spec" ([Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)), and the widely shared `grilling` skill in `mattpocock/skills`, which asks each round's questions with a recommended answer and leaves facts to the agent and decisions to the person.
  - In plan mode the agent interviews the engineer until the plan is concrete (page 19), then writes `plan.md` with the sections of page 20's example, Files that change, Order of work, Risks, and Proof, and answers in it the three questions of page 19, step 3, so an engineer who forgets to ask still reads the answers before approving.
  - The plan is ready when an engineer who never saw the conversation could implement the change from it alone (page 20, step 4).
  - Only an engineer's plan-mode session writes the first `plan.md`: the engineer starts that session (page 19, step 1) and accepts the plan (page 20, step 6), and the plan is logged "along with who accepted it" (page 20). So `plan.md` names the engineer who accepted it, the `write-spec` skill and the automated spec job stop at `spec.md`, and `REVIEW.md` flags a `plan.md` that names no engineer. A later change that departs from the plan, such as a fix the PR review loop pushes, updates `plan.md` in the same commit, as page 20, step 7 asks,, and a human approves the pull request through branch protection (page 39). An agent in auto mode wrote and pushed a `plan.md` for repository-rename after its spec merged, because nothing told it to stop at the spec, and the session ran in auto mode although `.claude/settings.json` sets `"defaultMode": "plan"`, so a default mode alone does not hold the rule. The review pass re-checks it at the pull request (page 26), but it can see only whether the plan names an engineer, so the code owner who approves the pull request confirms that the named engineer accepted it (page 39: "Approval comes from a human through branch protection"). In the root and in every template.
- **Requirements and design (15–17):** each policy skill holds the organization's policy. As page 25 says, "An engineer writes it from the policy owner's source of truth", the owner is named (each project names its policy owners in `CODEOWNERS`, as `SETUP.md` step 2 already asks, with the paths of the skills in `.claude/skills/`), and "When the policy changes, change the skill and have the policy owner sign off the change". Each `spec.md` names the commit at which it was written and quotes what the product owner's prompt added to the skill's prompt, which page 16, step 2 says "names the constraints", so the prompt, which the `write-spec` skill holds, and the policy skills in force can be read back from git at that commit (page 17). The `write-spec` skill and the automated spec job both write that record, in the root and in every template.
- **Give Claude a feedback loop (31–33):** every check that **Verifying your work** lists checks the project's real files, and the healthy output it names comes from a run that checked them; a check that cannot read the project fails instead of printing a pass. Once dependencies are installed, each verification command runs locally with one command and needs no other download, in the root and in every template. In the stacks with a UI, `AGENTS.md` tells the agent to open the changed page with the Playwright MCP, take a screenshot, look at it, and compare it with the approved mock when there is one (page 32, step 5), as MLflow (`mlflow/server/js/CLAUDE.md`), TrueNAS (`truenas/webui` `CLAUDE.md`), and OpenPanel (`AGENTS.md`) tell their agents. `AGENTS.md` names the `verifier` subagent in one line, as `macro-inc/macro` lists its subagents in its `CLAUDE.md`.
- **Continuous evals in CI (34–35):** evals run on every pull request that changes `CLAUDE.md`, `AGENTS.md`, skills, hooks, or `evals/`, and on a nightly schedule. The playbook names "CLAUDE.md, skills or hooks" (page 34, step 3), and its `agent-evals.yml` example filters on `CLAUDE.md` and `.claude/**` with a nightly cron (page 35); `AGENTS.md`, `.agents/`, and `evals/` are added because these projects keep their instructions in `AGENTS.md`, their rules and hooks in `.agents/`, and the eval cases in `evals/`; skills sit under `.claude/` (`intent/multi-agent-support/intent.md`). A change that lowers the pass rate is reviewed before it merges, and "The pass-rate threshold is enforced as a merge check" (page 34, step 4; page 35).
- **AI in the PR review loop, step 4 (38):** `@claude` on a review comment pushes a fix. On a pull request the agent opened, a review comment from any reviewer starts the babysit loop in CI by itself, with no one tagging `@claude`, whichever tool or person posted it: Claude Code Review, Cursor Bugbot, another review bot, or a person: page 38, step 4 says "For PRs Claude opened, go further and let Claude babysit the PR to merge", with a loop that "sweeps the unresolved review comments and failing checks on the PR, addresses them and pushes the fixes, until the PR is green and waiting only on code owner approval"; page 45, step 2 puts "addressing review comments" among the write steps CI runs "behind the existing gates"; and page 9 makes the automatic loop the end state. It runs in real time, not on a schedule and not from an open session: the job starts on GitHub's `pull_request_review` event (`submitted`) and, for a comment a person adds later, such as a reply that reopens a resolved thread or an `@claude` on an inline comment, on `pull_request_review_comment` (`created`), the two events Anthropic's official example listens to (`anthropics/claude-code-action` `examples/claude.yml`), so it starts as soon as each review arrives; unlike that example, it does not wait for an `@claude` mention. Because nothing waits for a mention, the job filters what starts it: one run per submitted review, which already carries that review's inline comments, so the comments that arrive with a review do not start their own runs, while a later comment by a person does; no run for a review or comment the agent wrote itself, so its replies do not restart the loop; no run for an approval; and one run at a time per pull request, through a `concurrency` group, so a new review waits for the running pass instead of racing it. The agent checks each finding and fixes what is real. It replies on every thread, saying what it changed or why it made no change, and then resolves that thread, so no comment is left without an answer; a person who disagrees reopens the thread. It never merges, and a person still approves through branch protection (page 39). Its pushes use the separate token the automated handover needs, because a push made with the repository's `GITHUB_TOKEN` starts no workflow. In the root and in every template. `REVIEW.md`'s compliance pass also checks the change against the brand, security, compliance, and UX policy skills (page 26), and the review flags a change that makes `AGENTS.md` outdated and proposes the correction when it flags the same mistake a second time (page 38, step 5).
- **Hooks as approval gates (40–41):** the production gate matches the command and environment the project actually deploys with.
- **CI/CD integration and deployment (44–46):**
  - Step 1: the templates get the "Triage failed build" job. The root, a public repository, keeps its triage job on workload identity federation, which it already has set up.
  - Step 3: every CI job that calls Claude, in the root and in every template, runs with an exact allowlist, the setup Claude Code documents for CI: `claude -p … --permission-mode dontAsk --allowedTools …`, where anything not allowed is denied ([Claude Code: Permission modes](https://code.claude.com/docs/en/permission-modes)), and that allowlist names no web tool such as `WebFetch`, whose requests do not pass through the shell sandbox's domain list, and holds no production credentials. For the network policy the step asks for, the job runs Claude Code's own sandbox, whose network allows only listed domains ("which start empty") and which needs `bubblewrap` and `socat` on Linux ([Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)); whether it runs on GitHub's Ubuntu runners is checked in the spec. GitHub's egress-firewall runner, a technical preview, waits until GitHub releases it.
  - Step 4: deploy, status, and rollback are tools exposed through MCP, scoped per environment.
  - Step 5: autonomy is tiered by environment, as page 45 sets it: "In development, the agent deploys freely. In production, the agent prepares the release and the release manager authorizes it", and staging "sits somewhere in the middle", here a person promotes a commit to `uat`. The agent may act up to the production gate and cannot pass it (page 46). Projects stay trunk-based: `main` deploys to `dev`, and a commit is promoted to `uat` and then `prod`. The production gate is the hook, as the playbook has it: "a hook enforces the production gate" (page 45, step 5) and "The production deploy hook blocks the release until a named release manager authorizes it" (page 46). On GitHub Team, the release manager authorizes a `prod` deploy by pushing a protected tag, as the official Next.js repository publishes on a `v*` tag push (`vercel/next.js` `.github/workflows/build_and_deploy.yml`, lines 4–10):
    - Pushing the tag starts the `prod` deploy, and the deploy ships the tagged commit itself: a tag push runs with `GITHUB_SHA` set to the "Tip commit pushed to the ref" ([GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). The deploy takes no commit as input, so no one can name another commit at run time.
    - The deploy first checks that the tagged commit is on `main` and reached `uat`, and stops otherwise. A tag push runs the workflow file from the tagged commit, "workflows that are not merged into the default branch" included (same page), so this check binds only when the tag is on a reviewed `main` commit; the ruleset below is what keeps anyone else from tagging. A release-team member who tags an unreviewed commit could still run a changed workflow with `prod` secrets; the spec checks whether GitHub Team offers an independent check before `prod` credentials are granted, and otherwise records this as the release team's trust.
    - A tag ruleset lets only the release team create, update, or delete that tag ("Restrict creations", "Restrict updates", "Restrict deletions", and "Block force pushes"), so an existing tag cannot be moved ([GitHub Docs: Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
    - The `prod` environment accepts deploys only from that tag pattern, and the deploy job no longer requires the `main` branch ref, which a tag run does not have.
    - The agent's own GitHub identity, such as the Claude GitHub App, is not on the ruleset's bypass list.
    - The template READMEs stop telling the team to add required reviewers, which a private repository on GitHub Team cannot use.
    - The tag ruleset checks who creates the tag; it does not require a second person. An agent that runs with a release team member's own access is held back by the production gate hook, so the organization deploys that hook in managed settings, where "individual engineers cannot switch them off" (page 40, step 3), without `allowManagedHooksOnly`: that key would "Run only the hooks your organization deploys" ([Claude Code: Settings reference](https://code.claude.com/docs/en/settings-reference)), which the playbook confirms means "nothing local can add to or replace them" (page 43), and the project keeps its own hooks: formatting after an edit, the block on skipping Git hooks, and the session-start reminder (`intent/lean-agent-setup/intent.md`). The README and `SETUP.md` say so.
    - Promotion deploys the image that `intent/monorepo-apps/intent.md` builds, by its digest, and reads GitHub's deployment records to find which commit of each app reached each environment (per app, because each changed app has its own image), in the monorepo every project is; it matches no job name or run title. A record GitHub creates for a job holds the run's own commit, which for a manual run on `main` is the tip of `main`, not the promoted commit, so each deploy records the commit it actually deployed; the REST API takes a commit SHA as a deployment's `ref` ([GitHub REST API: Deployments](https://docs.github.com/en/rest/deployments/deployments)). How is decided in the spec.
  - Step 6: rollback is one command, the same in every environment, that can be rehearsed in staging. It is a runbook of its own, separate from the release deploy, as page 45, step 4 names "Deploy, status, and rollback" as separate tools: it re-deploys an image digest that already ran in that environment, as GitHub's deployment records show, and accepts no other digest, so it can return an environment only to code that was released there before. The images stay in GitHub Container Registry (`intent/monorepo-apps/intent.md`). The protected tag still gates every release of new code into `prod`; the spec designs how the `prod` environment admits the rollback runbook as well. Railway's own rollback is not enough on its own: it "will revert to the previously successful deployment. Both the Docker image and custom variables are restored", but "A removed deployment that is outside of the retention policy will not have the option to rollback" ([Railway: Rollback](https://docs.railway.com/deployments/deployment-actions#rollback); [Railway: Image retention policy](https://docs.railway.com/pricing/plans#image-retention-policy)). Hosting platforms make rollback a single action in the same way, such as Vercel's Instant Rollback, `heroku rollback`, and `kubectl rollout undo`. In `dev` and `uat` the agent runs it itself. In `prod` the agent may trigger it too, because the rollback runbook is approved in advance: at the highest tier the agent may act "only by opening a PR into the review gate or triggering a pre-approved runbook" (page 49, step 3), "the runbooks the agent may trigger were approved in advance" (page 50), and "the agent triggers the existing rollback pipeline" when the post-deploy error rate breaches 3σ (page 51). The runbook holds the production credential and the agent only triggers it, so the agent still holds no production credentials of its own (page 45, step 3), and it reports each rollback where the team sees it, as in page 52's example. A rollback does not undo changes to data: Heroku warns that state stored in add-ons or externally is not rolled back ([Heroku Dev Center: Releases](https://devcenter.heroku.com/articles/releases)), and `SETUP.md` and the loop guide say so. In the root, which deploys no app and releases only an npm package, rollback points the `latest` tag back at the previous version and deprecates the bad one with a message that names the version to install instead: npm's own documentation says `npm install` without a version "installs the `latest` tag", that `npm dist-tag add` "Tags the specified version of the package with the specified tag", and, for removing a version, "Consider using the `deprecate` command instead" (`docs/content/commands/npm-dist-tag.md` and `npm-unpublish.md`, bundled with npm 10.9.9). The procedure is written down, and `bands.yaml`'s `runbook:rollback-deploy` names it. The spec checks whether the release workflow can run `npm dist-tag` and `npm deprecate` under trusted publishing or needs another credential.
- **Closing the loop, confidence gates (48):** when a stage runs without a person starting it, an independent gate checks its output before the next stage starts, either a deterministic check or a separate reviewing agent that argues against the output, and sends the work on or to a person (page 48).
- **Closing the loop (48–51):** the first control band watches the CI test failure rate, the metric of the playbook's own `bands.yaml` example (page 50: `metric: ci_test_failure_rate`, `baseline: rolling_30d`, `rules: western_electric`), which needs only the CI system's API. A breach is handled by tier as that example sets: log at 1σ, diagnose read-only at 2σ, and at 3σ propose a pull request or trigger the approved rollback runbook (step 6 above); the finding is written as the next `intent.md`.
- **Claude Tag and the lessons file (52):** projects have `lessons/`, where the post-mortem is written.

- **How to measure it (every play):** for each play the project has, the loop guide page below names the playbook's leading and lagging indicators and where each is read, and `SETUP.md`'s OpenTelemetry step names the indicators it feeds, starting with the time spent waiting at each gate, which page 44 reads from the hook decisions in the OpenTelemetry export.

- **The root:** the spec lists every play and says whether it applies to the root and why, so "where it applies" is decided once. Where a generated project keeps an outcome in `apps/docs`, the spec names the root's place for it, such as `CONTRIBUTING.md`. The root names its policy owners in `.github/CODEOWNERS`, and its product owner as the owner of `/intent/`, as the templates' `SETUP.md` step 2 does, because "The product owner approves, and the accept or reject decision that sends the intent into Stage 2: Design is recorded as the merge or the closing review" (page 13); today `* @joetakara @next-friday-engineer` lets either owner approve an intent. The spec checks how the product owner approves an intent pull request that the product owner opened, because the agent opens pull requests from the account it works under, and records its source of truth for each artifact, as page 22 asks and the templates' `SETUP.md` step 6 does.

- **Entering the loop:** every generated project's documentation site (`apps/docs`, as `intent/monorepo-apps/intent.md` sets it up) has a page that links to Anthropic's official playbook and lists, for each stage of the loop (Plan, Design, Build, Test, Deploy, Maintain), who acts and which file, skill, or command in the project carries that stage out. The page links to the playbook rather than copying its text, because the playbook is Anthropic's document.

- **Entering the loop, status:** every generated project has a skill that lists each change in `intent/`, the stage it is in, the gate it waits on, who acts next, and the next step, read from which artifacts exist, their `Status:` lines, and their pull requests. A change that is stuck shows as blocked, with what blocks it: a pull request whose checks wait for **Approve workflows to run**, a handover job that failed, or a check that could not run. Community implementations of the playbook ship the same: `/ai-sdlc-status` in `ghiaog123/ai-native-sdlc` and `/loops:next` in `hoha-dev/loops`. It encodes a repeated step of the loop, not a policy, as the playbook's own slash command for babysitting a pull request does (page 38, step 4), so it needs no policy owner: "Repeat processes are encoded via skills" (page 11).

- **Entering the loop, reminder:** when a Claude Code session starts, a `SessionStart` hook adds the same summary to the session, because Claude Code adds such a hook's output "as context that Claude can see and act on" and the hook has "No blocking or decision control" ([Claude Code: Hooks](https://code.claude.com/docs/en/hooks)). `ghiaog123/ai-native-sdlc` re-injects the loop state at the start of every session the same way. The reminder only informs and blocks nothing, so local enforcement stays small (`intent/lean-agent-setup/intent.md`). Whether Cursor offers an equivalent is checked against Cursor's documentation in the spec.

- **Entering the loop, setup:** every generated project has a setup skill that reads `SETUP.md`, does each step an agent can do in that session, and lists the steps that need a person, with who does each, as `SETUP.md` names them. The steps live only in `SETUP.md`; the skill holds none of its own. It exists so a new project enters the loop with the agent doing every setup step it can; every new project runs the same setup, a repeated process, and "Repeat processes are encoded via skills" (page 11).

## Constraints

- The agent may act up to the production gate and cannot pass it (page 46).
- Agent jobs in CI hold no production credentials (page 45, step 3). Their Claude API key is the one departure from that step's short-lived, scoped tokens.
- CI work that is not a playbook play, such as Turborepo, the scanners, and how the root's CI jobs are laid out, belongs to `intent/ci/intent.md`; how CI builds images with Turborepo belongs to `intent/ci/intent.md`, and deploying them by digest to `intent/monorepo-apps/intent.md`; who may promote to each environment, and the gate before `prod`, belong here.

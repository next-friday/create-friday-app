# Plan: Ship the SDLC playbook as the `friday` plugin (from intent.md 2026-11-12)

Accepted by: @joetakara.

The work lands as three pull requests, in this order. Each one leaves `main` working. The release that carries the change to generated projects comes after the third.

This plan departs from the spec in four places. The first is by the engineer's decision: `claude plugin eval` runs the eval cases, and `run-agent-evals.ts` is deleted. The same commit changes requirements 1, 20, and 21 of `spec.md` to say so. The second: a **Gate** step keeps its words except the path of a playbook and the name of the command, which the move changes, and requirement 15 of `spec.md` says so. The third: the eval cases and the subagent's tool fields are specific to one tool, so they sit in the adapters, in `plugins/friday/adapters/claude-code/evals/` and `plugins/friday/adapters/agents.json`, and requirement 3 holds for the source alone. The same commit changes requirements 1 and 4 of `spec.md` and its layout to say so, by the product owner's decision. The layout follows `cursor/plugins`, where one source renders a tree for each tool and a file only one tool reads sits in that tool's tree (`harness/pstack/README.md`). The fourth is by the product owner's decision: the checks do not ship as an npm package. A generated project keeps `scripts/check-plan.ts`, `scripts/check-bands.ts`, and `scripts/measure-loop.ts`, copied by the CLI as today, so `plan:check` and `bands:check` run in CI with no agent tool and no extra package, and the plugin's source holds the same scripts for this repository. The same commit changes requirements 9 and 20 of `spec.md`, its area of concern 1, and its table of changed files to say so.

The product owner added one requirement while this plan was written, and the same commit adds it to `spec.md` as requirement 27: a reply gives the full URL of each pull request, issue, branch, workflow run, and file on the host that it names, and its **Status** line gives the URL of the page where the person acts next.

## Risks

- **What could break.** A session in this repository or in a generated project has no `sdlc` skill until the plugin is installed. Step 10 and step 14 are where that shows.
- **The riskiest step is 10.** One file a person commits must land on the branch before it merges. Without `.claude/settings.json` the repository loses its own loop, and `pnpm plugin:check` fails until it is committed.
- **A plugin change reaches every project at once**, as the spec's area of concern 4 says. Step 6 puts the eval cases in front of every such change.
- **The official eval runner costs model calls**: each case runs with the plugin and again without it. The plan runs it by hand, with `--runs 1` and the small model, and in no workflow. `pnpm evals:run` grants `Write` and `Edit` and runs the cases tagged `no-shell`. `pnpm evals:run:write` also grants `Bash` and runs the cases tagged `needs-write`; `claude plugin eval` runs `Bash` only under an OS sandbox.
- **The Cursor adapter is proved by a person, once** (step 15). The render script checks only its shape against `pstack`.
- Options not taken:
  - Keeping `run-agent-evals.ts`. The official runner reads the same case layout and adds the comparison without the plugin.
  - One pull request. A change of this size is hard to review and waits as a whole on its slowest part.
  - Leaving the Cursor adapter for later. The spec asks for both tools from one source.
  - Changing `scripts/sync-agent-rules.ts`. It already renders nothing when `.agents/skills/` holds no file, and it still renders a project's own policy skill.

# Intent: CI that follows the playbook and Turborepo's guidance

Author: Joe Takara (Developer Productivity). Status: draft.

## Problem

The CI in this repository and in the templates has drifted from the AI-native SDLC Playbook and from Turborepo's official guidance. It works, but it is the traditional kind: deterministic scripts only, with every judgment step left to a person.

## Proposed outcome

- CI does what the playbook's CI plays describe: evals run when the agent's configuration changes, a failed build gets a triage summary, `@claude` on a review comment pushes a fix, and rollback is one rehearsed command.
- Evals run both on every pull request that changes `CLAUDE.md`, `AGENTS.md`, skills, hooks, or `evals/`, and on a nightly schedule, as the playbook's `agent-evals.yml` example shows (pages 34–35).
- The agent may act up to the production gate and cannot pass it, and the gate matches how the project really deploys.
- Promotion reads GitHub's deployment records to find which commit reached each environment, in `base` and `turborepo`; it matches no job name or run title. A record GitHub creates for a job holds the run's own commit, which for a manual run on `main` is the tip of `main`, not the promoted commit, so each deploy records the commit it actually deployed; the REST API takes a commit SHA as a deployment's `ref` ([GitHub REST API: Deployments](https://docs.github.com/en/rest/deployments/deployments)). How is decided in the spec.
- Projects stay trunk-based: `main` deploys to `dev`, and a commit is promoted to `uat` and then `prod`.
- On GitHub Team, the production gate is a protected tag:
  - Pushing the tag starts the `prod` deploy, and the deploy ships the tagged commit itself: a tag push runs with `GITHUB_SHA` set to the "Tip commit pushed to the ref" ([GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). The deploy takes no commit as input, so no one can name another commit at run time.
  - The deploy first checks that the tagged commit is on `main` and reached `uat`, and stops otherwise. A tag push runs the workflow file from the tagged commit, "workflows that are not merged into the default branch" included (same page), so this check binds only when the tag is on a reviewed `main` commit; the ruleset below is what keeps anyone else from tagging.
  - A tag ruleset lets only the release team create, update, or delete that tag ("Restrict creations", "Restrict updates", "Restrict deletions", and "Block force pushes"), so an existing tag cannot be moved ([GitHub Docs: Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
  - The `prod` environment accepts deploys only from that tag pattern, and the deploy job no longer requires the `main` branch ref, which a tag run does not have.
  - The agent's own GitHub identity, such as the Claude GitHub App, is not on the ruleset's bypass list.
  - This gate checks who creates the tag; it does not require a second person. An agent that runs with a release team member's own access is held back only by the local hook, which is a convenience, not a boundary. The README and `SETUP.md` say so.
- CI follows Turborepo's official guidance: it finds changed apps with `turbo query affected`, runs checks with `turbo run --affected`, builds images with `turbo prune --docker`, and names no app in code.
- The root CI runs every check in one job, `pnpm verify`, the same command the pre-push hook runs, as the templates' CI already does. It keeps the jobs that test the product: Template, Consumer Smoke, and Compatibility. The Release Integrity job is removed: on the release pull request it repeats format, `package.json` order, build, and publint, which the same run already checks (`.github/workflows/ci.yml`, lines 55–57 and 321–343).
- Scanners:
  - The templates keep Semgrep (`sast.yml`) for static analysis and OSV-Scanner for dependency vulnerabilities, because both run on a private repository without a license. CodeQL and Dependency Review run only when the repository is public or has GitHub Code Security, as `codeql.yml` already does; `dependency-review.yml` gets the same condition.
  - Keep both secret scanners: gitleaks runs fast at commit time and in CI, and holds the payment card (PAN) rules in `.gitleaks.toml`, which stay in every template even though no template handles payments, because client projects may, and card numbers can leak through fixtures, logs, or copied test data, a company decision that no playbook page covers; TruffleHog in CI checks whether a found secret is still live.
  - Keep diff-cover for the templates' patch coverage gate: it runs inside CI with no paid service, which private projects need. The root keeps Codecov, which is free for this open-source repository. A Vitest threshold cannot replace either, because it measures the whole project, not the changed lines.
  - Keep Trivy, hadolint, zizmor, Scorecard, and the pull request title check; none overlaps another tool.
  - Remove the `changes` label from `.github/labeler.yml`.
- A CI decision that departs from the playbook or from a tool's official documentation records the reason in that change's `spec.md` or `plan.md`, which the playbook commits as the audit trail (pages 7 and 20).
- The root and every template have a rule in `.agents/rules/`, scoped to `.github/**`, that tells an agent how to write a workflow safely, following the Next.js `.github/AGENTS.md`. It is rendered for Claude Code and Cursor like the other scoped rules. Where the Next.js advice conflicts with a workflow here, such as `pr-triage.yml` using `pull_request_target`, the spec decides.
- Every CI job that calls Claude, in the root and in every template, passes `--permission-mode auto`, allows only the tools that job needs, and holds no production credentials. The egress-firewall runner waits until GitHub releases it.

## Affected users and systems

- This repository's `.github/workflows/`.
- Every template's `.github/workflows/`, `.github/scripts/`, Dockerfiles, and `SETUP.md`.
- Each consumer's Claude API budget, because evals, triage, and the fix loop call the API.

## Constraints

- Workflow files at the root of this repository cannot be pushed from an agent session; a person commits them.
- Claude API access uses an API key secret.
- Related intents: `intent/restore-playbook-plays/intent.md` covers the plays outside CI, and `intent/monorepo-apps/intent.md` covers CI for apps at `apps/<group>/<app>`, the remote cache, and image promotion.

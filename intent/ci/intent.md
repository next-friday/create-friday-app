# Intent: CI that follows Turborepo's guidance and fits private client projects

Author: Joe Takara (Developer Productivity). Status: accepted.

## Problem

The CI in this repository and in the templates does not follow Turborepo's official guidance or fit what a private client repository can run. The CI steps the AI-native SDLC Playbook describes, such as evals, triage, the `@claude` fix loop, the production gate, and rollback, are plays, and `intent/playbook-plays/intent.md` covers them.

## Proposed outcome

- CI follows Turborepo's official guidance and names no app in code; this intent owns how CI runs Turborepo, and `intent/monorepo-apps/intent.md` owns the app layout:
  - `turbo query affected` lists the changed apps, and every per-app job (end-to-end tests, container image, deploy) runs as a matrix over that list. Turborepo's documentation has no matrix example; the matrix is a common community pattern on GitHub Actions, where one job finds the changed apps and the next builds its matrix from them ([WarpBuild](https://warpbuild.com/blog/github-actions-monorepo-guide); [OneUptime](https://oneuptime.com/blog/post/2025-12-20-dynamic-matrix-github-actions/view)). The checkout keeps enough Git history to compare against: "if the checkout is too shallow, all packages will be considered changed" (`crafting-your-repository/constructing-ci.mdx`), and Turborepo's GitHub Actions guide uses `fetch-depth: 2`.
  - Checks run as `turbo run` tasks with `--affected`.
  - Each app lints itself, as Turborepo's ESLint guide sets it up: every package has its own `eslint.config` and a `lint` script running `eslint .`, the `lint` task in `turbo.json` has `"dependsOn": ["^lint"]`, and the root runs `turbo run lint` (`docs/guides/tools/eslint.mdx`). Each ESLint process then loads only its own app's TypeScript project, so each process stays at one app's size however many apps the monorepo has, and a raised Node heap is not needed. Turborepo runs up to 10 tasks at once by default (`--concurrency`, "Default: `10`", `docs/reference/run.mdx`), so CI sets `--concurrency` low enough that the lint processes running together fit the runner's memory.
  - Container images build with `turbo prune <app> --docker`, so a dependency change in one app does not rebuild another.
- The root CI keeps its checks in separate jobs by kind, as other projects do (`anthropics/anthropic-sdk-typescript`: lint, build, test; `anthropics/claude-code-action`: test, prettier, typecheck; `withastro/astro` and `vitejs/vite` likewise), and drops the Release Integrity job: on the release pull request it repeats format, `package.json` order, build, and publint, which the same run already checks (`.github/workflows/ci.yml`, lines 55–57 and 321–343).
- Each change runs the checks for what it touches, in the root and in every template, at pull request time and on the push to `main`:
  - A change to Markdown or to other files that do not affect the running app runs Prettier and ESLint, whose Markdown rules check the `.md` files, and the secret scanners; it skips type checking, tests, the build, the image, the deploy, Semgrep, and OSV-Scanner. A change to code runs everything. This is what the official Next.js repository does: its `changes` job sets `docs-only`, its tests and native builds run only when `docs-only` is false, and `lint` and `validate-docs-links` run on every change (`vercel/next.js` `.github/workflows/build_and_test.yml`).
  - A check is skipped by a job condition, not by `paths` or `paths-ignore`, and one final job stays the required check: GitHub says a workflow skipped by path filtering leaves its checks "in a 'Pending' state" that "block merging", while "A job is skipped by a conditional" reports "Success" ([GitHub Docs: Troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), from `github/docs`).
  - In the monorepo templates, Turborepo decides which tasks a change affects instead of a hand-written filter: each task lists its `inputs`, for example `"inputs": ["$TURBO_DEFAULT$", "!README.md"]`, and with `futureFlags.affectedUsingTaskInputs` "`--affected` operates at the **task level**: a task is only selected if the changed files match its `inputs` configuration" (`turbo` 2.11.10 `docs/reference/configuration.mdx`). `apps/docs` is the exception: its Markdown is the site's content, so a change to it builds and deploys the docs site.
- Scanners:
  - The templates hold only what a private repository on a GitHub Team organization can run without buying an add-on: CodeQL (`codeql.yml`), Dependency Review (`dependency-review.yml`), and Scorecard (`scorecard.yml`) are removed from the templates. The templates do static analysis with Semgrep (`sast.yml`) and check dependencies with OSV-Scanner on each pull request that changes code or dependencies, because both run on a private repository without a license; Dependabot's alerts are available for private repositories, but they do not cover these projects today: "When pnpm writes `pnpm-lock.yaml` as two YAML documents, the dependency graph does not detect the dependencies in that file. This is the default format for pnpm 12 projects that pin a pnpm version", and Dependabot alerts and security updates are then not created ([GitHub Docs: Supported ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories)); the root's `pnpm-lock.yaml` and the templates' pinned pnpm are in that case. OSV-Scanner is therefore the dependency vulnerability check in the templates. The root, a public open-source repository, keeps every check GitHub offers it free: CodeQL code scanning, Dependency Review, and Scorecard. Dependency Review reads the dependency graph, which cannot read the root's two-document `pnpm-lock.yaml`; GitHub lists `package.json` as an additional file for pnpm (GitHub Docs: Dependency graph supported package ecosystems, from `github/docs`), so at most the root's direct dependencies are reviewed. The spec checks what it actually reports on a pull request that changes a dependency.
  - Keep both secret scanners: gitleaks runs fast at commit time and in CI, and holds the payment card (PAN) rules in `.gitleaks.toml`, which stay in every template even though no template handles payments, because client projects may, and card numbers can leak through fixtures, logs, or copied test data; TruffleHog in CI checks whether a found secret is still live.
  - Keep diff-cover for the templates' patch coverage gate: it runs inside CI with no paid service, which private projects need. The root keeps Codecov, which is free for this open-source repository. A Vitest threshold cannot replace either, because it measures the whole project, not the changed lines.
  - Keep Trivy, hadolint, zizmor, and the pull request title check. The root also runs actionlint and zizmor on every template's workflow files, on each pull request that changes them, by passing those paths as arguments, so a template workflow that would fail to start is caught before it ships. In the templates, zizmor and actionlint (both in `zizmor.yml`) check the workflow files; in the root, CodeQL also checks them, and Scorecard scores the root's security posture as a whole.
  - Remove the `changes` label from `.github/labeler.yml`.
- The root and every template have a rule in `.agents/rules/`, scoped to `.github/**`, that tells an agent how to write a workflow safely, following the Next.js `.github/AGENTS.md`. It is rendered for Claude Code and Cursor like the other scoped rules. Where the Next.js advice conflicts with a workflow here, such as `pr-triage.yml` using `pull_request_target`, the spec decides.

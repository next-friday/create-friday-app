# Intent: GitHub files that fit private client projects

Author: Joe Takara (Developer Productivity). Status: accepted.

## Problem

The templates ship a full set of GitHub files: README, contributing guide, security policy, code owners, pull request template, issue forms, Dependabot, and labeler. Some of them assume a public repository, but most generated projects are private client repositories.

## Proposed outcome

- `SECURITY.md` names a contact the team sets during setup, such as the security email of the company or of the client, and `SETUP.md` has a step to fill it in. Private vulnerability reporting is removed from the templates' `SECURITY.md` and `SETUP.md`, because GitHub offers it only for public repositories; the root, a public repository, keeps it.
- The templates' `SETUP.md` turns on secret scanning and push protection only for an organization that has GitHub Secret Protection, which a private repository needs for them; gitleaks and TruffleHog stay the templates' secret scanners. The root, a public repository, can use both features free.
- The root and every template have a documentation report issue form, with the same fields as the Next.js form and the labels `documentation` and `needs triage`.
- `.git-blame-ignore-revs` is added, in the root or in a generated project, in the commit right after the first commit that only reformats code, because a commit cannot list its own hash, and lists that commit and each later one; no project carries an empty file.

## Affected users and systems

- Every project generated from the CLI, and anyone who finds a vulnerability in one.
- `templates/base/SECURITY.md`, `templates/base/SETUP.md`, and the issue forms and Git files the outcomes name.

## Constraints

- A generated project must still pass its own `pnpm verify`.

# Intent: Add the playbook plays the templates miss

Author: Joe Takara (Developer Productivity). Status: draft.

## Problem

A play-by-play check of the templates and the root on `main` against the AI-native SDLC Playbook found plays that are missing or incomplete. The playbook groups its plays by stage; "these steps are modular", and "Each play names its dependencies under 'Prerequisites'" (page 8), so a play is adopted after the plays it depends on.

## Proposed outcome

Every play the playbook describes is present in the templates, and in the root where it applies, or its absence is recorded with the playbook page and the reason. By play, in the playbook's stage order:

- **Intent home (12–13):** every change keeps its intent, spec, and plan in its own folder in `intent/`, where the playbook commits them as the audit trail (pages 7 and 20); none is deleted or moved, as in the community repositories that implement this playbook (`imsungbin/ai-native-sdlc-playbook`, `matthew-js-porter/spring-petclinic-ai-native`, `jsnkle/ai-native-sdlc`), which keep one folder per change in `intent/`.
  - A folder is named `<YYYY-MM-DD>-<change>`, so the folder sorts by date. A running number, as in `imsungbin/ai-native-sdlc-playbook` (`intent/0001-bootstrap-playbook-repo/`), sorts the same way, but two branches can take the same number.
  - Each intent's `Status:` line, which the playbook's example starts at `draft` (page 12), shows where the change stands: `draft`, `accepted`, `done`, `withdrawn`, or `replaced by intent/<folder>/`. The agent or the CI job that carries out each step writes the line in the pull request it opens, not a person by hand.
  - A rejected intent never becomes a file, because closing its pull request rejects it (`templates/base/intent/README.md`). A problem found after a change ships starts a new intent, as the playbook's closing loop does (page 48), instead of editing the old one.
  - The write-intent skill and `intent/README.md` describe this, in the root and in every template.
- **Automated handover (5, 9, 16):** when an intent's pull request merges, a non-interactive CI job runs the spec pass with the organization's skills loaded and opens `spec.md` as a pull request, as page 16, step 2 describes, so "the product owner's first involvement is the review". The job runs with the same exact allowlist (step 3 below) and the same Claude credentials as the project's other Claude jobs: an API key in the templates, workload identity federation in the root. A community implementation of the playbook ships such a job as `spec-on-intent-merge.yml` (`jsnkle/ai-native-sdlc`, `plugin/template/.github/workflows/`). The decisions stay with people, where the playbook puts them: the product owner accepts the intent and the spec (page 16, step 6), and the engineer approves the plan in plan mode (page 19). In the root and in every template.
- **Requirements and design (15–17):** each policy skill holds the organization's policy. As page 25 says, "An engineer writes it from the policy owner's source of truth", the owner is named (each project names its policy owners in `CODEOWNERS`, as `SETUP.md` step 2 already asks), and "When the policy changes, change the skill and have the policy owner sign off the change".
- **Give Claude a feedback loop (31–33):** every check that **Verifying your work** lists checks the project's real files, and the healthy output it names comes from a run that checked them; a check that cannot read the project fails instead of printing a pass. Once dependencies are installed, each verification command runs locally with one command and needs no other download.
- **Continuous evals in CI (34–35):** evals run on every pull request that changes `CLAUDE.md`, `AGENTS.md`, skills, hooks, or `evals/`, and on a nightly schedule. The playbook names "CLAUDE.md, skills or hooks" (page 34, step 3), and its `agent-evals.yml` example filters on `CLAUDE.md` and `.claude/**` with a nightly cron (page 35); `AGENTS.md`, `.agents/`, and `evals/` are added because these projects keep their instructions in `AGENTS.md`, their skills and hooks in `.agents/`, and the eval cases in `evals/`. A change that lowers the pass rate is reviewed before it merges, and "The pass-rate threshold is enforced as a merge check" (page 34, step 4; page 35).
- **AI in the PR review loop, step 4 (38):** `@claude` on a review comment pushes a fix.
- **Hooks as approval gates (40–41):** the production gate matches the command and environment the project actually deploys with.
- **CI/CD integration and deployment (44–46):**
  - Step 1: the templates get the "Triage failed build" job. The root, a public repository, keeps its triage job on workload identity federation, which it already has set up.
  - Step 3: every CI job that calls Claude, in the root and in every template, runs with an exact allowlist, the setup Claude Code documents for CI: `claude -p … --permission-mode dontAsk --allowedTools …`, where anything not allowed is denied ([Claude Code: Permission modes](https://code.claude.com/docs/en/permission-modes)), and holds no production credentials. For the network policy the step asks for, the job runs Claude Code's own sandbox, whose network allows only listed domains ("which start empty") and which needs `bubblewrap` and `socat` on Linux ([Claude Code: Sandboxing](https://code.claude.com/docs/en/sandboxing)); whether it runs on GitHub's Ubuntu runners is checked in the spec. GitHub's egress-firewall runner, a technical preview, waits until GitHub releases it.
  - Step 4: deploy, status, and rollback are tools exposed through MCP, scoped per environment.
  - Step 5: autonomy is tiered by environment, as page 45 sets it: "In development, the agent deploys freely. In production, the agent prepares the release and the release manager authorizes it", and staging "sits somewhere in the middle", here a person promotes a commit to `uat`. The agent may act up to the production gate and cannot pass it (page 46). Projects stay trunk-based: `main` deploys to `dev`, and a commit is promoted to `uat` and then `prod`. On GitHub Team, the production gate is a protected tag, as the official Next.js repository publishes on a `v*` tag push (`vercel/next.js` `.github/workflows/build_and_deploy.yml`, lines 4–10):
    - Pushing the tag starts the `prod` deploy, and the deploy ships the tagged commit itself: a tag push runs with `GITHUB_SHA` set to the "Tip commit pushed to the ref" ([GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). The deploy takes no commit as input, so no one can name another commit at run time.
    - The deploy first checks that the tagged commit is on `main` and reached `uat`, and stops otherwise. A tag push runs the workflow file from the tagged commit, "workflows that are not merged into the default branch" included (same page), so this check binds only when the tag is on a reviewed `main` commit; the ruleset below is what keeps anyone else from tagging.
    - A tag ruleset lets only the release team create, update, or delete that tag ("Restrict creations", "Restrict updates", "Restrict deletions", and "Block force pushes"), so an existing tag cannot be moved ([GitHub Docs: Available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)).
    - The `prod` environment accepts deploys only from that tag pattern, and the deploy job no longer requires the `main` branch ref, which a tag run does not have.
    - The agent's own GitHub identity, such as the Claude GitHub App, is not on the ruleset's bypass list.
    - The template READMEs stop telling the team to add required reviewers, which a private repository on GitHub Team cannot use.
    - This gate checks who creates the tag; it does not require a second person. An agent that runs with a release team member's own access is held back only by the local hook, which is a convenience, not a boundary. The README and `SETUP.md` say so.
    - Promotion reads GitHub's deployment records to find which commit of each app reached each environment (per app, because `intent/monorepo-apps/intent.md` deploys each changed app's own image), in `base` and `turborepo`; it matches no job name or run title. A record GitHub creates for a job holds the run's own commit, which for a manual run on `main` is the tip of `main`, not the promoted commit, so each deploy records the commit it actually deployed; the REST API takes a commit SHA as a deployment's `ref` ([GitHub REST API: Deployments](https://docs.github.com/en/rest/deployments/deployments)). How is decided in the spec.
  - Step 6: rollback is a single command that the agent can run and that is rehearsed in staging.
- **Closing the loop (48–51):** the first control band watches the CI test failure rate, the metric of the playbook's own `bands.yaml` example (page 50: `metric: ci_test_failure_rate`, `baseline: rolling_30d`, `rules: western_electric`), which needs only the CI system's API. A breach is handled by tier as that example sets: log at 1σ, diagnose read-only at 2σ, and at 3σ propose a pull request or trigger the approved rollback runbook; the finding is written as the next `intent.md`.
- **Claude Tag and the lessons file (52):** projects have `lessons/`, where the post-mortem is written.

- **How to measure it (every play):** for each play the project has, the loop guide page below names the playbook's leading and lagging indicators and where each is read, and `SETUP.md`'s OpenTelemetry step names the indicators it feeds.

- **Entering the loop:** every generated project's documentation site (`apps/docs`, as `intent/monorepo-apps/intent.md` sets it up) has a page that links to Anthropic's official playbook and lists, for each stage of the loop (Plan, Design, Build, Test, Deploy, Maintain), who acts and which file, skill, or command in the project carries that stage out. The page links to the playbook rather than copying its text, because the playbook is Anthropic's document.

- **Entering the loop, setup:** every generated project has a setup skill that reads `SETUP.md`, does each step an agent can do in that session, and lists the steps that need a person, with who does each, as `SETUP.md` names them. The steps live only in `SETUP.md`; the skill holds none of its own. It exists so a new project enters the loop with the agent doing every setup step it can; the playbook's rule for skills covers knowledge applied again and again, not a one-time task (page 25).

Across the plays:

- Every job in the templates that calls the Claude API uses an API key secret instead of workload identity federation, as the playbook's eval example does (pages 34–35). This departs from page 45, step 3, which asks for short-lived, scoped tokens, and from Anthropic's own repositories, which use workload identity federation (for example `anthropics/claude-code-action`, `.github/workflows/issue-triage.yml`). That change's `spec.md` and `plan.md` record the departure and its reason: workload identity federation needs setup the team chose not to take on.
- A later change that removes or weakens part of a play starts from its own `intent.md`, which says why (page 11), so the reason stays in the audit trail (page 7).

## Affected users and systems

- Every project generated from the CLI: its CI and deploy workflows, `SETUP.md`, README, hooks, and folders; and this repository's own CI where a play applies to it.
- Each consumer's Claude API budget, because evals, the fix loop, and triage call the API.
- Policy owners, whose written policy an engineer turns into each of the four policy skills, and who sign off its changes.
- Release teams, who own the production tag.

## Constraints

- The agent may act up to the production gate and cannot pass it (page 46).
- Agent jobs in CI hold no production credentials (page 45, step 3). Their Claude API key is the one departure from that step's short-lived, scoped tokens.
- CI work that is not a playbook play, such as Turborepo, the scanners, and how the root's CI jobs are laid out, belongs to `intent/ci/intent.md`; images and their promotion belong to `intent/monorepo-apps/intent.md`.
